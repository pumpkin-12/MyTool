### 实测数据（重要，日后可复用）
- 项目总 **8 603 MB / 10 736 文件**，其中 `src-tauri/target/` 独占 **8 595.8 MB（99.7%）**。
  - `target/debug` = **6 490 MB**：incremental 966 MB、deps 3 624 MB、build 731 MB、`toolbox.pdb` 109.9 MB、`toolbox_lib.lib` 691.8 MB、`libtoolbox_lib.rlib` 283 MB
  - `target/release` = **2 105 MB**：deps 1 737 MB（`toolbox_lib.lib` 116.9 MB、`libwindows*.rlib` 各 86.6 MB）、build 358 MB；**交付物仅 `toolbox.exe` 4.2 MB + NSIS 安装包 2.2 MB**
  - debug 比 release 胖 3 倍（调试符号 + 无 LTO）
- **非 target 全部文件只有 49 个 / 约 8.1 MB** —— 源码和库根本不是问题
- 体积 TOP：`web/vendor/mermaid.min.js` 3.41 MB、`web/vendor/xlsx.full.min.js` 0.84 MB、`web/index.html` 0.22 MB、`data/store.json` ×4 份 0.72 MB
- `store.json` 键分布：`quiz:questions` 159.1 KB（88.4%）、`quiz:records` 14.5 KB、`internlog:items` 1.9 KB、**`sketch:shapes` 仅 0.2 KB（画板目前无图片，最大的隐患还没爆）**
- git 已很干净：只跟踪 35 文件、`.git` 2.1 MB；`target/`、`gen/schemas/`、`data/`、`_*.txt` 均已忽略
- 项目外：`.cargo\registry` 1 351 MB（全部 Rust 项目共享）、`%LOCALAPPDATA%\tauri` 6.8 MB（NSIS 工具链，**保留可离线打包**）、`%APPDATA%\com.lijiazhen.toolbox` 0.26 MB（旧数据目录，最后写入 9/11，**可删**）
- 磁盘水位：C 可用 103.6 GB；**D 可用 42.9 GB（80%）** ← target 是唯一压力源

### 方案三档
1. **第一档（零风险，回收 8.6 GB）**：`cargo clean --profile dev`（回收 6.5 GB）+ 手工删 `target/release/{deps,build,.fingerprint,*.pdb,*.lib,*.rlib,*.d}`（回收 2.1 GB，**务必保留 `toolbox.exe` 与 `bundle/nsis/`**）+ 删 C 盘旧数据目录 + 提交当前未提交改动
2. **第二档**：
   - **画板图片外置（最值得做）**：图片落 `data/assets/<sha1>.<ext>`，`shapes` 只存 `asset://` 引用；否则插 10 张图 store.json 就到 10 MB，且题库/日志每次改动都要重写这 10 MB
   - 存档按 key 拆分（配合上一条，写盘量从全量 181 KB 降到单键）
   - **mermaid 精简：建议不做** —— 省 2 MB 却要引入 Node 构建步骤，破坏项目最核心的「零构建」约定
3. **第三档**：cargo 缓存外置（影响全局，C 盘不紧张就不动）、target 定期清理自动化、`.cargo/config.toml` 的 `build.target-dir` 外置开关

### 清理后的预期
项目 8 603 MB → **约 15 MB**；D 盘可用 42.9 → **约 51.5 GB**；文件数 10 736 → **约 160**；交付物不变。

## 补充：运行期占用实测（用户追问「运行过程中内容的占用」）

用户发任务管理器截图：`PersonalToolbox (7)` / 90.2 MB / 0% CPU / 0 Mbps。实测拆解：

### 进程构成（7 个进程，合计约 353 MB 工作集）
| 进程 | 内存 | 说明 |
|---|---:|---|
| `toolbox.exe`（Rust 宿主） | 27.4 MB（私有仅 7.3 MB） | 很轻，无泄漏无空转 |
| webview2 `--embedded-browser-webview` | 124.4 MB | 浏览器主进程 |
| webview2 `--type=renderer` | 69.2 MB | **前端代码真正跑在这里** |
| webview2 `--type=gpu-process` | 63.0 MB | 画板 canvas |
| webview2 `--type=utility` network | 32.9 MB | |
| webview2 `--type=utility` storage | 20.5 MB | |
| webview2 `--type=crashpad-handler` | 16.1 MB | |

主进程 exe 实际是 `target/release/toolbox.exe`（用户开的是便携版）；user-data-dir = `C:\Users\DELL\AppData\Local\com.lijiazhen.toolbox\EBWebView`。
系统内存：总 15.7 GB / 可用 4.0 GB / 已用 74%。

**关键判断**：236 MB 是 WebView2 固定架构开销（主+GPU+网络+存储+crashpad），**动不了**，进程数也降不下来，每个 WebView2 应用都这样。**只有 renderer 的 69 MB 可影响。**

### 🔴 新发现的真问题：mermaid 常驻内存
`index.html:3439` —— **进 Mermaid 工具页就立刻 `loadLib()`**，加载 3.41 MB 压缩源码并常驻；`dispose()` 只清定时器，**`lib` 变量和 WebView2 模块缓存都不释放**。
→ 只要进过一次 Mermaid 页，**60~100 MB 就一直挂着直到关应用**。

**修正了此前结论**：之前按磁盘体积（3.41 MB）判断「mermaid 精简不做」是**片面的**。改判为 → **不裁剪包体（仍不做打包器），改为「按需加载 + 离开释放」**（约 20 行前端，只动 `loadLib` / `dispose`），预期 renderer 从 69 MB 降到 20~35 MB。

### WebView2 数据目录 38 MB（C 盘）
`EBWebView` = 38.0 MB / 321 文件。其中对本应用（纯离线、无网络）**零价值**的：`Subresource Filter` 12.3 MB + `Speech Recognition` 2.6 MB + `BrowserMetrics` 1.2 MB = **16.1 MB**。
可优化：`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--disable-component-update --disable-background-networking --disable-breakpad`（在 `run()` 里 WebView2 初始化前 `set_var`）。
已确认该目录**不含 `store.json`**，与 D 盘应用数据互不干扰。
