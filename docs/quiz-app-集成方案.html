把 D:\Ai-file\quiz-app（Spring Boot + Vue 2 刷题系统）作为第四个工具接入本地工具箱。

2026-09-11 源：quiz-app（2 次提交 / 48 项未提交改动） 目标：MyTool（Tauri 2 · 便携版 3.93 MB）

01结论先行

这次和前三个工具（实习日志 / 画板 / Mermaid）不是同一类问题。那三个天生就是「一段 JS + 一个本地存档」，塞进去就行。quiz-app 是一个服务端应用：Spring Boot 后端 + Vue 2 SPA + 数据库。

先说一句不太顺耳的话：quiz-app 现在根本不持久化数据。application.yml 里 dev 环境的库是 jdbc:h2:mem:quizdb——内存模式，注释自己都写着「应用重启后数据丢失」。所以无论你选哪个集成方案，第一步都不是集成，而是先让它把数据存下来。否则接进工具箱也只是一个每次重启就清空的刷题器。

推荐路径：方案 C（保留 Vue 界面，把数据层本地化），分两档走。下面把四个方案的代价摊开。

同日修正：本文档原推荐方案 C，读了源码之后改为推荐方案 D（重写）。 原因是原判断建立在"前端 UI 是真实工作量、后端有 28 KB 逻辑要翻译"这两个印象上，逐个文件看过之后两个印象都不成立。详细依据见第 08 节。第 03–07 节保留原样，作为决策过程的记录。

02两边的架构，摆在一起看

维度个人工具箱 MyToolquiz-app
形态 纯客户端。Tauri 2 壳 + 一个零构建单文件 web/index.html 服务端。Spring Boot 2.7.18（Java 11）跑在 8081，Vue SPA 由它托管
数据 单个 JSON 存档 %APPDATA%\com.lijiazhen.toolbox\store.json，key 前缀 toolbox:<tool>:<field> dev 用 H2 内存库（重启即丢）；prod 用 MySQL（需外部服务）

前端 vanilla JS 单文件，约 3400 行，无框架无构建 Vue 2.7 + Vue Router 3 + Vuex 3 + Element UI 2.15，Vue CLI 构建，dist 1.89 MB（不含 sourcemap）
接口面 无（工具直接读写 AppStore） 5 个 Controller，约 19 个 REST 端点
硬约定 不引入 Vite/Webpack 等打包器，前端永远是零构建单文件 已经依赖 Webpack 构建链

三处结构性错位

  1. 进程模型：工具箱是单进程单窗口；quiz-app 要额外拉一个 JVM。
  2. 数据归属：工具箱的一切都在那份存档里，能用首页「导出全部数据」整体搬家；quiz-app 的数据在数据库里，跟工具箱的存档体系毫无关系。
  3. 体量量级：把一个 43 MB 的 jar 加一个 JRE 塞进一个 3.93 MB 的应用，等于换了种软件形态。

但也有三个对集成非常有利的事实

1. 前端只有一个 API 收口。frontend/src/api/request.js 是一个 axios 实例（baseURL: '/api' + 响应拦截器解包 res.data），所有 api/*.js 都走它。要"换掉后端"，只需要替换这一个文件的导出。

2. 路由是 hash 模式。new VueRouter({ routes }) 没有设 mode: 'history'，所以用的是 #/dashboard 这种形式——静态文件直接就能跑，不需要服务器做 URL 重写；放进 iframe 后它有自己的 hash 命名空间，不会和工具箱自己的 #tool/<id> 路由打架。

3. Excel 导入在后端没有参与。importQuestions(questions) 传的是解析好的数组，xlsx 库在前端浏览器里解析。所以后端的 Java 代码一行都不碰 Excel，本地化时这部分完全不用管。

03四个方案

方案 ASidecar：整套搬进去

用 Tauri 的 bundle.externalBin 把 Java 启动器 + jar 作为子进程打包，应用启动时拉起后端，工具界面用 iframe 指向 localhost:8081。

  • Java 逻辑、Vue 界面一行都不用改。
  • 应用体积从 3.93 MB 涨到 约 100 MB（43 MB jar + jlink 精简 JRE 约 45–55 MB）。涨 25 倍。
  • 要额外处理：端口被占用、iframe 要等后端 ready 再加载、退出时确保子进程被杀干净、H2 嵌入式文件库的多进程锁冲突。
  • Tauri 2 的 sidecar 需要开 shell 插件权限，能力模型要放宽。
工作量 小体积代价 +95 MB数据归属 工具箱之外风格一致性 差
方案 B外置后端，工具箱只挂入口

后端 jar 保持独立运行（手动启，或做成开机自启），工具箱里加一个工具，内容就是一个指向 http://localhost:8081 的 iframe。

  • 改动最小，工具箱体积不变。
  • 但严格说这不是"加入"，是"挂了个快捷方式"：后端没起来就白屏，用户得知道先去启服务。
  • 数据仍在数据库里，和工具箱的存档、导出、迁移体系完全脱节。
  • 适合"先看看效果"的过渡验证，不适合当终态。
工作量 极小体积代价 0数据归属 工具箱之外风格一致性 差
方案 C保留 Vue 界面，把数据层本地化推荐

前端 UI 全部复用，砍掉 Spring Boot。把 request.js 一个文件换成本地实现（那 19 个端点用 JS 重写），数据读写走工具箱的 AppStore。构建出的 dist 放进 web/quiz/，工具箱里用 iframe 承载。

  • UI 工作量全部保住——BankPanel.vue 18 KB、QuizPanel.vue 12 KB，加上 6 个 view、6 个 component，重写是纯浪费。
  • Java 那部分要翻译成 JS：QuizService 15.9 KB + QuestionService 5.5 KB + StatsService 4 KB + WrongQuestionService 1.9 KB，合计约 28 KB 逻辑。而且 Java 版可以留着当规格说明书，QuizServiceTest.java（31 KB）和 逻辑测试报告.md（26 KB）直接就是现成的验收用例。
  • 体积只增加 1.89 MB（dist 去掉 sourcemap 后；含 map 是 8.73 MB，别直接拷）。作为参照：vendor/mermaid.min.js 已经占了 3.5 MB，同一个量级。
  • 数据真正并入统一存档——刷题、实习日志、画板共用一份文件，共用首页的「导出全部数据」。这是唯一能做到"真正加进工具箱"的方案。
  • iframe 天然隔离 Element UI 的 206 KB CSS，不会污染工具箱现有样式。
工作量 中体积代价 +1.9 MB数据归属 工具箱内风格一致性 中（iframe 独立）
需要你点头的一点：工具箱的硬约定是「不引入打包器」。方案 C 会让仓库里出现一个 Vue CLI 的构建产物。折中办法是把 Vue 源码留在 quiz-app 仓库，工具箱只收 dist，当作 vendor 资源对待——和 mermaid.min.js 同级，不在工具箱里跑 npm。要不要接受这个破例，你定。
方案 D纯前端重写

彻底丢开 Vue 和 Element UI，用 vanilla JS 按工具箱现有风格重写，逻辑照 Java 抄。

  • 结果最一致：真·单文件、零依赖、和其他三个工具浑然一体，没有 iframe。
  • 但银行面板那种「题型 Tab + 分类管理 + 批量编辑 + Excel 导入」的界面要全部重做，工作量最大。
  • 如果方案 C 走顺了，其实可以后续再把 C 演进成 D（先把数据层本地化，再逐步把界面搬出来）。两者不冲突。
工作量 大体积代价 0数据归属 工具箱内风格一致性 最好

04推荐路线：方案 C，分两档

本节推荐已被第 08 节修正。方案 C 的"分两档"步骤本身仍然成立（先本地化数据层、再接进工具箱），但第 1 档之后的走向应当直接进入重写，而不是长期停留在 iframe 形态。
第 0 档让 quiz-app 自己先能存住数据

和工具箱无关，但无论最后选哪个方案都得做。目标是：java -jar 单跑，重启后题库和记录还在。

  1. dev 的 H2 改成文件模式。把 jdbc:h2:mem:quizdb 换成 jdbc:h2:file:${user.home}/.quiz-app/quizdb，数据就落到磁盘了。一行改动。
  2. 注意 H2 文件库的锁。嵌入式模式同一时刻只允许一个进程打开。如果以后真走方案 A（sidecar），工具箱和手动启的后端不能同时开着同一个库。
  3. 先把那 48 项未提交改动提交掉。quiz-app 目前只有 2 个提交、48 项未提交。集成过程要动 request.js 和构建产物，不清干净没法分辨哪块是谁改的。
第 1 档本地 API 适配层

在 quiz-app 仓库里把后端换成 JS 实现，前端仍然是一套正常的 Vue 应用，只是数据不再走 HTTP。

  1. 新增 frontend/src/api/local.js，实现全部 19 个端点的本地版本。接口形状对齐 Java：返回 { code: 200, message, data }，这样现有的响应拦截器不用改。
  2. request.js 改成二选一分发：检测到本地模式走 local.js，否则走原来的 axios。保留 axios 分支是为了你以后还能跑前后端分离的开发模式。
  3. 数据落到工具箱的 AppStore，key 用 toolbox:quiz:questions / :sessions / :records / :wrong 这类前缀，和现有三个工具并列。
  4. 用 Java 的测试当验收：QuizServiceTest（31 KB）、QuestionServiceTest、StatsServiceTest 里的用例逐条对到 JS 实现上。
第 2 档打包进工具箱

让「刷题」出现在工具箱首页，点进去就能用。

  1. npm run build，只把非 .map 的文件拷到 web/quiz/（1.89 MB，别把 6.8 MB 的 sourcemap 一起带进去）。
  2. 在 web/index.html 的 registry 里 registerTool 第四个工具，mount() 渲染一个 <iframe src="quiz/index.html">。
  3. 首页卡片沿用现有风格加一个图标（颜色和图标可复用 #7F77DD 那套紫色系）。
iframe 的一个好处：Element UI 的 CSS 和工具箱自己的 CSS 完全隔离，不会互相污染。这也是为什么选 iframe 而不是直接把 Vue 应用内联进来——两套 UI 框架的样式放在同一个 document 里迟早出事。

06几个要提前想清楚的技术点

问题说明与对策
存档体量 工具箱现在每次保存都会把整个存档 stringify 一遍再写盘。题库如果上千题，假设每题 300 字节 JSON 就是 300 KB，再加上不断累积的答题记录和错题，这份存档会长得很快，连带影响实习日志和画板的保存性能。建议趁这次把 quiz 的数据拆成独立文件——这正好就是工具箱第 2 档「存档按 key 拆分」要解决的问题，两件事可以合并做。
localStorage 同源 iframe 和父页面都是 tauri://localhost，共享同一个 localStorage。所以如果本地适配层图省事直接用 localStorage，要么统一走 AppStore（父页的存储层），要么给 key 加独立前缀，否则会和工具箱的 toolbox:* 体系互相干扰。
别拷 sourcemap frontend/dist 含 map 是 8.73 MB，去掉之后 1.89 MB。差的 6.8 MB 全是调试用的 sourcemap，发布时没有价值。构建时可以在 vue.config.js 里关掉 productionSourceMap。
Element UI 体积 chunk-vendors.js 1.14 MB（Vue + Element UI + Vuex + axios + xlsx 全在里面）、562.js 437 KB（xlsx 单独分包）、CSS 206 KB。想瘦身可以做体积优化，但不是这一步的重点。
CSP 与 iframe Tauri 配置里 csp: null（不注入策略），所以 iframe 加载本地静态文件不受限，不用额外开权限。
开发态怎么调 内嵌后调试 iframe 里的 Vue 应用不太方便。建议保留两条路：request.js 的双分支让 quiz-app 依然能 npm run serve + 后端分开跑，用浏览器调；工具箱里跑的是本地模式。两边共用一个界面代码库。

08修正 · 为什么我现在更推荐重写

原判断建立在两个印象上：「前端 UI 是真实工作量，重写是浪费」和「后端有约 28 KB 逻辑要翻译」。逐个文件读过之后，两个印象都不成立。

一、后端要搬的不是 28 KB Java，而是大约 200 行真实规则

我把 4 个 Service 按「去掉 import / 空行 / 注解 / 注释后的实义行数」统计了一遍，再逐个读内容：

文件总行实义行其中真正的领域规则
QuizService366291约 90–110 行
QuestionService14099约 40 行
StatsService9068约 40 行
WrongQuestionService5430约 15 行
合计650488约 185–205 行

剩下的几百行是什么？五参数构造器注入、DTO ↔ 实体映射、Repository 调用、JsonProcessingException 包装、响应对象逐字段赋值。这些东西存在的唯一理由是「前后端分离 + ORM」——在一个本地单用户应用里没有网络边界，它们全部消失。

真正要保住、也最容易在重写时漏掉的规则只有这么几条：

  • 抽题策略：分类过滤 → 题型过滤（先校验题型合法）→ 四种模式。其中 exam 洗牌后取前 N、random 全洗牌、custom 可选洗牌后取前 N、order 保持原序；题量都要 max(1, min(count, size)) 夹紧。
  • 可判题判定：只有 choice 和 truefalse 判对错，fill / essay 不判。
  • normalizeTrueFalseAnswer：把 对 / 正确 / TRUE / T 统一归一成 A，其余一律算 B。这是带历史数据兼容的属性，重写最容易漏——漏了就会让判断题全部判错。
  • 计分分母只算可判题：score = round(correct × 100 ÷ judged)，填空和简答不拉低正确率。
  • 错题本同步时机有两处：单题提交时（答对则移除、答错则计数 +1），以及交卷时把未答的可判题也补进错题本。后者很容易漏。
一个有意思的发现：后端自己已经在用「JSON 塞进数据库列」的写法——session.questionIds、session.answers、record.answerDetails 全都是 Jackson 序列化成字符串存进 TEXT 列。也就是说这个应用的数据模型本来就是 JSON。搬进工具箱的存档不是一次迁移，而是回归它天然的形态。

BankPanel 那个"18 KB"打开一看，几乎全是 el-card / el-select / el-table / el-table-column / el-dialog / el-upload / el-form 这些组件标签的声明式堆叠。真正的领域 UI 只有四件事：按题型分 4 个 Tab、一个工具栏（导入 / 模板 / 添加 / 清空）、一张表（只有选择题多出 A/B/C/D 四列，靠 v-if="tab.key === 'choice'" 控制）、两个弹窗（导入、增删改）。

三、Excel 这个唯一的硬依赖，成本比我以为的低

我把 node_modules 翻了一遍：SheetJS 的可离线分发构建 xlsx.full.min.js 是 861 KB。放进 web/vendor/ 就行——作为参照，mermaid.min.js 已经占了 3.5 MB。不需要退化成 CSV，你"用 Excel 出题库"的工作流可以完整保留。

四、方案 C 的真正问题是它会长期悬在那里

C 的收益（复用 UI）是眼前的，代价（仓库里多一套 Vue + 构建链、和工具箱"零构建单文件"的约定长期冲突）是持续的。更麻烦的是：走 C 之后，迁移到 D 的动因会一直存在，但永远不会被排期——因为"已经能用了"。结果就是工具箱里永久住着一个长得不像自己、还要跟着 npm 一起升级的 iframe。

而 D 是唯一不破坏"零构建"硬约定的方案，结束后 quiz 就和实习日志、画板、Mermaid 完全同质。

五、重写的最大风险，有现成的对冲手段

重写最怕的是丢业务规则。但 QuizServiceTest.java（31 KB）和 逻辑测试报告.md（26 KB）就是现成的验收清单，逐条翻译成 Node 断言即可。这套办法在同一天已经验证过有效——工具箱那次就是靠把 AppStore 源码抠进 Node 的 vm 跑双模式断言，才抓住了写盘竞态和失败不可见两个问题。

修正后的推荐路线

第 0 档在 quiz-app 里把领域逻辑抽成与框架无关的纯 JS
