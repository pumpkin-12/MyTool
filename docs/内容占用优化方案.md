# 个人工具箱 · 内容占用优化方案

> 盘点时间：2026-09-14（含运行期实测）
> 盘点对象：`D:\Ai-file\MyTool`（含 git 仓库、构建产物、应用数据、第三方库）+ 运行中的应用（进程内存 / WebView2 数据目录）
>
> **结论先行**
> - **磁盘**：项目 8.6 GB 里，99.7% 是 Rust 构建缓存（`src-tauri/target`，8 595.8 MB）。真正的「项目内容」只有约 8 MB。**优化重心是构建产物治理，不是瘦身源码或第三方库。**
> - **内存**：运行时常驻约 353 MB，其中 **236 MB 是 WebView2 的固定门票**（浏览器主进程 + GPU + 网络 + 存储，动不了）；Rust 宿主只有 27.4 MB；**唯一能大幅改善的是 mermaid 的 60~100 MB —— 问题不在包体大小，而在「进页就加载、离开不释放」的加载时机。**
> - **一句话**：磁盘的敌人是 `target/`，内存的敌人是 mermaid 的加载时机。**两者都不需要牺牲「零构建」约定。**

### 1.7 运行期占用（进程内存 + WebView2 数据目录）

#### 1.7.1 进程构成实测（应用开着时的任务管理器）

任务管理器显示 `PersonalToolbox (7)` —— **7 个进程**，实测拆解如下：

| 进程 | PID 层级 | 工作集内存 | 说明 |
|---|---|---:|---|
| `toolbox.exe` | 主进程 | **27.4 MB** | Rust 宿主，只有 7.3 MB 私有内存 |
| `msedgewebview2.exe` | `--embedded-browser-webview`（父） | 124.4 MB | WebView2 浏览器主进程 |
| `msedgewebview2.exe` | `--type=renderer` | 69.2 MB | **渲染进程 —— 前端代码真正跑在这里** |
| `msedgewebview2.exe` | `--type=gpu-process` | 63.0 MB | 独立的 GPU 进程（画板 canvas 用） |
| `msedgewebview2.exe` | `--type=utility` network | 32.9 MB | 网络服务 |
| `msedgewebview2.exe` | `--type=utility` storage | 20.5 MB | 存储服务（IndexedDB/LocalStorage） |
| `msedgewebview2.exe` | `--type=crashpad-handler` | 16.1 MB | 崩溃收集 |
| **合计** | **7 个进程** | **约 353 MB** | 任务管理器显示 90.2 MB 是按「应用组」合并后的口径 |

**结论**：
- **Rust 侧很轻**（27.4 MB，0% CPU，0 Mbps 网络），说明后端没泄漏、没空转。
- **354 MB 里的 92% 是 WebView2 自身的固定开销** —— 浏览器主进程 + GPU 进程 + 网络/存储服务 + 崩溃处理，这 4 个加起来 236 MB，是**每个 WebView2 应用都要付的"门票"**，与我们的代码无关。
- 只有 **69.2 MB 的 renderer** 是我们能影响的。而其中**绝大部分是 mermaid**（见下）。

> 参照：一个空白 WebView2 应用冷启动大约就是 250~300 MB。

#### 1.7.2 mermaid 是 renderer 内存的大头（可优化）

`index.html:3439` —— **进入 Mermaid 工具页时立即 `loadLib()`**：

```js
loadLib().then(() => { if (!disposed) requestRender(true); }).catch(() => {});
```

`viaLocal()` 把 3.41 MB 的 `mermaid.min.js` 作为 `<script>` 注入 → WebView2 用 JS 引擎**解析并常驻 3.41 MB 压缩源码**。mermaid 内部有大量图表定义、布局引擎（dagre/elk）、KaTeX 风格的文本度量表，解压后常驻内存可达 **60~100 MB**，且**离开工具页后不会释放**（`dispose` 只是清定时器，`lib` 变量和 WebView2 的模块缓存都还在）。

**这条值得优化**，方案见 §3.12。

#### 1.7.3 WebView2 数据目录：38 MB 的浏览器缓存（在 C 盘）

`C:\Users\DELL\AppData\Local\com.lijiazhen.toolbox\EBWebView`，**与 D 盘的应用数据无关**（已确认里面**没有** `store.json`，两者互不干扰）。

| 子目录 | 体积 | 说明 |
|---|---:|---|
| `Subresource Filter` | **12.3 MB** | 广告/追踪拦截规则库，最大单项（单文件 4.83 MB） |
| `Default` | 9.8 MB | 含 `Cache/Cache_Data`（Web 缓存）+ Code Cache |
| `component_crx_cache` | 4.6 MB | 组件自动更新缓存 |
| `GrShaderCache` | 4.6 MB | GPU 着色器编译缓存（`data_3` 单独 4.01 MB） |
| `Speech Recognition` | 2.6 MB | 语音识别组件，**本项目完全用不到** |
| `hyphen-data` | 1.7 MB | 断字词典 |
| `BrowserMetrics` | 1.2 MB | 遥测指标 |
| 其余（ShaderCache / PKIMetadata / Trust Protection Lists 等） | ~1.2 MB | |

**两个关键事实**：
1. **`Subresource Filter` 12.3 MB + `Speech Recognition` 2.6 MB + `BrowserMetrics` 1.2 MB = 16.1 MB 对本应用零价值。** 前者是给浏览器拦截恶意子资源用的，后者是语音识别，本项目一个 `fetch` 都不发（CSP 为 `null`、无网络功能）。
2. **这个目录会持续增长** —— `Default/Cache` 随每次打开应用累积，`BrowserMetrics` 随会话累积。38 MB 只是当前值。

## 3. 优化方案

按「收益 / 风险」排序，分三档。**每档可独立执行，互不依赖。**

### 🥇 第一档：零风险，立刻做（回收约 8.6 GB）

#### 3.1 清理构建产物（回收 8.6 GB）

**这是唯一能真正解决 D 盘水位问题的动作。**

```bash
# 目标：删掉 debug 全部产物（6.5 GB），release 保留最终 exe 和安装包
cd D:\Ai-file\MyTool\src-tauri

# ① 删 debug（收益 6.5 GB，下次 tauri dev 重新编译，约 3~5 分钟）
cargo clean --profile dev

# ② 清 release 中间产物，保留 exe 与 bundle（收益约 2.1 GB，下次出包全量重编）
#    注意：cargo clean --release 会连 exe 一起删，所以手工删子目录
Remove-Item -Recurse -Force target\release\deps, target\release\build, target\release\.fingerprint
Remove-Item -Force target\release\*.pdb, target\release\*.lib, target\release\*.rlib, target\release\*.d

# ③ 保留清单（务必不要删）
#    target\release\toolbox.exe                          ← 便携版，4.2 MB
#    target\release\bundle\nsis\PersonalToolbox_*.exe    ← 安装包，2.2 MB
```

**风险**：极低。`target/` 全部是可重建产物，源码和数据都在别处。
**代价**：下次 `tauri dev` 冷启动编译变慢（本项目约 3~5 分钟，含 LTO 的 release 更久）。

**建议**：删除前先把旧目录整个压缩一份放到 `D:\Ai-file\MyTool\data\_archive\`，彻底无害。

### 🥈 第二档：低风险，按需做（回收约 5~15 MB + 提升写性能）

#### 3.5 存档按 key 拆分（改 Rust + AppStore）

**现状**：13 个键挤在一个 `store.json`。改一行草稿，也要把 160 KB 的题库一起 stringify + 写盘。

**方案**：
- Rust 侧 `store_write(data)` 改为 `store_write(key, value)`，每个 `toolbox:*` 键写一个独立文件到 `data/keys/<safe-key>.json`
- 或者保持单文件，但新增 `store_write_patch(patch)`，只传变更的键

**推荐做法**：新增一对命令 `kv_read_all` / `kv_write(key, value)`，前端 `AppStore.persist()` 改成收集本次变更的键集合，只写变更的：

```js
// AppStore 内部
let dirty = new Set();
function persist() {
  const payload = {};
  dirty.forEach(k => { payload[k] = clone(mem[k]); });
  dirty.clear();
  // → invoke('kv_write_many', { patch: payload })
}
```

**收益**：
- 写盘量从「全量 181 KB」降到「单个键 0.1~160 KB」，画板/日志操作几乎瞬时
- 存档不再是一个失败全丢的大文件
- **配合 3.7 的图片外置后，题库和画板互不干扰**

**成本**：约 60 行 Rust + 30 行前端，需同步改 `store_read` 兼容旧格式（读旧 `store.json` 做一次性迁移）。
**风险**：中。属于存储层改动，必须跑 `tools/verify-appstore.js` 全绿后再上真机。

#### 3.6 `data/` 备份策略收敛

**现状**：`store.json` + `.1`（30 分钟前）+ `.2`（1 天前）+ `.3`（1 天前），共 4 份 × 180 KB = 720 KB。

**优化**：备份不必全量复制。改为：
- `.1`：全量（最近一次，用于快速回滚）
- `.2` / `.3`：只在内容变化超过阈值时轮转，或改为**每天一个**（按日期命名，超 7 天清理）

**收益**：从 4 份降到 2~3 份，约省 360 KB。**说实话收益很小**，除非配合 3.7 的图片，否则优先级不高。

#### 3.7 画板图片外置为文件（**最值得做的一条**）

**现状**：插入图片 → `toDataURL` → base64 内联进 `shapes` → 进 `store.json`。最大边压到 1600px，单张大约几百 KB ~ 1 MB base64。

**问题**：插 10 张图，`store.json` 就到 10 MB，而**题库、日志的每一次改动都要重写这 10 MB。**

**方案**：
1. 图片不内联，落盘到 `data\assets\<sha1>.<ext>`
2. `shapes` 里只存 `{ type: 'image', src: 'asset://<sha1>.png' }`
3. 前端渲染时通过 Tauri 的 `convertFileSrc()` 或自定义命令读取

**收益**：
- `store.json` 恒定在百 KB 级，与图片数量解耦
- 图片去重（同一张图插 3 次只存 1 份）
- 与 3.5 配合后，画板写盘从「MB 级」降到「KB 级」

**成本**：Rust 加 2 条命令（`asset_put(base64) -> hash` / `asset_get(hash) -> base64`）+ 前端 `insertImageFile` 改写 + 导出 JSON 时需内联膨胀（保持可移植）。
**风险**：中高。涉及画板的读写与导出路径，必须覆盖「插入 / 渲染 / 导出 PNG / 导出 JSON / 导入 JSON / 撤销重做」全链路。

#### 3.8 mermaid 精简（**重新评估：改为"延后加载"而非"裁剪"**）

> ⚠️ 本条在 §1.7.2 之后**结论有调整**：原来只按磁盘体积（3.41 MB）判断「不做」，
> 但实测发现它**常驻 renderer 内存 60~100 MB**，是运行期占用里唯一我们能大幅改善的一项。
> 处理方式改为 **3.12 延后加载 + 释放**，而**不是**裁剪包体（裁剪仍需打包器，依然不做）。

**现状**：`web/vendor/mermaid.min.js` 3.41 MB，包含全部图表类型（flowchart / sequence / class / state / gantt / ER / pie / git / mindmap / timeline / sankey / quadrant / block / packet / architecture / radar / treemap …）。

**本项目实际用到的**（见 `TEMPLATES`，index.html:2908-2915）：流程图、时序图、类图、状态图、甘特图、ER 图 —— **6 种**。

**方案 A（裁剪包体）**：用 esbuild 自定义构建，只打包 6 类图，体积可降到约 1.5 MB。
- 成本：需要引入 Node 构建步骤（**违反「零构建」硬约定**）
- 风险：mermaid 内部图表注册机制耦合较深，裁剪后可能出现运行时错误
- **结论：不做。** 省 2 MB 磁盘、约 30 MB 内存，却要典当项目最核心的约定，不划算。

#### 3.9 `docs/*.html` 归档（回收 0.08 MB）

按新约定「方案一律用 Markdown」，把 `tauri-迁移方案.html`、`quiz-app-集成方案.html` 转为 `.md` 或移到 `docs/archive/`。

**收益**：极小。**纯整理性质，不急。**

#### 3.10 mermaid 改为「按需加载 + 可释放」**（运行期最大收益）**

**现状问题**（`index.html:3439`）：

```js
loadLib().then(() => { if (!disposed) requestRender(true); }).catch(() => {});
//              ↑ 进入工具页就立刻加载 3.41 MB 的 mermaid，且永不卸载
```

退出工具页时 `dispose()` 只做这些：

```js
return function () {
  disposed = true;
  renderSeq++;
  clearTimeout(renderTimer); clearTimeout(saveTimer); clearInterval(themeWatch);
  closeMenu();
  if (lib) { try { lib.initialize({ startOnLoad: false, securityLevel: 'strict' }); } catch (e) {} }
};
//              ↑ lib 变量、WebView2 的 <script> 与模块缓存，全都留着
```

**后果**：只要进过一次 Mermaid 页，那 60~100 MB 就一直挂在 renderer 上，直到关掉整个应用。

**方案**（纯前端，不动 Rust，不破坏零构建）：

1. **延后到真正需要时再加载**：进入工具页只渲染一个「点击加载」占位（或检测到用户开始输入/按 Ctrl+Enter 时再加载）。首屏不再付出 3.41 MB 解析代价。
2. **离开页面后释放引用**：`dispose()` 里执行 `lib = null`，并移除注入的 `<script>` 标签；`loadLib()` 的缓存 `loading` 也一并清空，下次进来重新加载。
   - 注意：V8 的脚本编译缓存仍在，二次加载会比首次快得多，**体感损失极小**。
3. **可选加分项**：`memory` 观察 —— 若 renderer 超过某阈值，在切走时提示「已释放 Mermaid 以回收内存」。

**收益**：
- 不用 Mermaid 的场景（大多数时候）：**省 60~100 MB 内存 + 减少首屏解析**
- 用过再切走：**内存可回收到接近基线**
- 磁盘体积**不变**（仍然 3.41 MB，这是离线优先的必要代价）

**成本**：约 20 行前端改动，集中在 `loadLib` / `dispose` 两处。
**风险**：低。需要覆盖「首次进入 / 切走再切回 / 加载中切走 / 加载失败重试」四种路径。

### 🥉 第三档：长期治理

#### 3.11 WebView2 数据目录裁剪（回收约 16 MB，**在 C 盘**）

**现状**：`%LOCALAPPDATA%\com.lijiazhen.toolbox\EBWebView` = 38.0 MB。其中对纯离线、无网络功能的应用**完全无用**的部分：

| 子目录/文件 | 体积 | 为何无用 |
|---|---:|---|
| `Subresource Filter\` | 12.3 MB | 拦截恶意子资源，本应用不发任何请求（CSP 为 `null`，无 fetch） |
| `Speech Recognition\` | 2.6 MB | 语音识别组件，用不到 |
| `BrowserMetrics\*.pma` | 1.2 MB | 遥测指标，可关 |
| **小计** | **16.1 MB** | |

**方案 A（推荐）**：Tauri 侧给 WebView2 传启动参数，**禁用不需要的组件**。WebView2 支持通过环境变量或 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 传参：

```
--disable-features=msSmartScreenProtection,SpeechRecognition  (示意，需按实际特性名验证)
--disable-component-update        (停掉 component_crx_cache 自动下载，省 4.6 MB)
--disable-breakpad                (停掉 Crashpad，省 16 MB 进程内存)
```

在 `lib.rs` 的 `run()` 最前面设置：

```rust
// 必须在 WebView2 初始化前设置
std::env::set_var("WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS",
    "--disable-component-update --disable-background-networking --disable-breakpad");
```

**方案 B（简单粗暴）**：定期删除缓存子目录。**必须先关掉应用**，否则文件被占用。

```powershell
# 关掉应用后再执行
$eb = "$env:LOCALAPPDATA\com.lijiazhen.toolbox\EBWebView"
Remove-Item -Recurse -Force "$eb\Subresource Filter", "$eb\Speech Recognition", "$eb\Default\Cache"
```

**收益**：16 MB（C 盘）+ 一条 Crashpad 进程（约 16 MB 内存）。
**风险**：方案 A **低但需实测** —— 参数名依赖 WebView2 版本（本机 152.0.4191.66），写错只是不生效、不会崩。方案 B 无风险但会随使用重新生成。
**说明**：这条属于「锦上添花」。38 MB 在 C 盘 103 GB 可用面前不算问题，**主要是为了少 1 个进程、少一点常驻内存**。

#### 3.12 `cargo` 依赖缓存外置（回收 1.35 GB，**但不是本项目的**）

`%USERPROFILE%\.cargo\registry` 占 1 351 MB，是所有 Rust 项目共享的依赖源码缓存。

**如果 C 盘紧张**：
```bash
# 把整个 cargo 家目录搬到 D 盘，然后设环境变量
setx CARGO_HOME "D:\Ai-file\cargo-home"
# 手动把 %USERPROFILE%\.cargo 内容搬过去
```
**注意**：这会影响到你所有的 Rust 项目，不只是工具箱。**C 盘还有 103 GB，不建议动。**

#### 3.13 给 `target/` 加「定期清理」自动化

`target/` 会持续膨胀。建议加一条每月自动清理：

- 每月 1 号清理 `target/debug`（保留 release 交付物）
- 或在 `data/` 旁边记录一个「上次清理时间」，超过 30 天且 debug > 5 GB 时提醒

#### 3.14 `.cargo/config.toml` 把 target 指向 D 盘其它位置

如果将来 D 盘也紧张，可以：
```toml
# D:\Ai-file\MyTool\.cargo\config.toml
[build]
target-dir = "D:\\Ai-file\\MyTool-build\\target"
```
把构建产物挪出项目目录，`target/` 不再污染仓库视图。
**当前不必要**（已在 D 盘），但值得知道这个开关。

## 6. 一句话结论

**磁盘上**：别去瘦身源码和库 —— 那总共就 8 MB。真正吃掉 8.6 GB 的是 `src-tauri/target/`，而它 100% 可重建。第一档三个动作**半小时内可完成，回收 8.6 GB，零功能风险**。

**内存上**：353 MB 里有 236 MB 是 WebView2 的固定门票（浏览器主进程 + GPU + 网络 + 存储），**动不了也不该动**；Rust 宿主只有 27.4 MB，**已经很轻**。唯一值得下手的是 **mermaid 那 60~100 MB 常驻内存** —— 而这不需要裁剪库、不需要打包器，只是把「进页就加载、永不释放」改成「需要时加载、离开时释放」，约 20 行前端代码。

**一句话**：磁盘的敌人是 `target/`，内存的敌人是 mermaid 的加载时机。**两者都不需要牺牲项目的「零构建」约定。**
