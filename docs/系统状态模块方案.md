# 个人工具箱 · 系统状态模块方案

> 起草：2026-09-14
> 需求：新增一个「系统配置 / 系统状态」模块，能查看当前系统状态（内存占用、磁盘占用等）
> 目标读者：本项目维护者（你最了解自己要什么，以下都按"可选"设计，不必全做）

---

## 0. 结论速览

| 问题 | 答案 |
|---|---|
| **能拿到真实数据吗？** | **能。** 所需 Win32 API 全部来自 `windows-sys 0.61.2`（包已在本地缓存，**无需联网下载**）；但需在 `Cargo.toml` 显式声明并勾选 feature，见 §7.5.1 |
| **要装 sysinfo 这类 crate 吗？** | **不需要。** `sysinfo` 未缓存、`ntapi` 也未缓存，会引入新的下载与编译时间。自己调 Win32 更划算（约 150 行 Rust） |
| **和前几轮的关注点有关系吗？** | **有，而且很直接。** 这个模块能把「上次那 8.6 GB 在哪、mermaid 到底占多少」变成**看得见的数字**，不用再靠任务管理器猜 |
| **建议做多大？** | **三档。** 第一档（推荐）只读展示，约 200 行；第三档才涉及写操作 |
| **最大风险** | 轮询采样的**定时器**——本项目已经因为 mermaid 常驻内存吃过一次亏，新模块绝不能重复"开了就不关" |
| **还有别的 API 可用吗？** | **有，已逐个核对源码，见 §7.5。** 最值得加的是 `GetPerformanceInfo`（进程数/线程数/系统缓存一次全给） |

## 1. 现状盘点（决定了怎么做）

### 1.1 现有工具注册机制

```js
// index.html:713
function registerTool(tool) { registry.push(tool); }
const ENABLED_TOOLS = ['internlog', 'sketch', 'mermaid', 'quiz'];
function isEnabled(t) { return ENABLED_TOOLS.indexOf(t.id) >= 0; }
```

- 新工具只需 **① 写 `registerTool({...})`，② 把 id 加进 `ENABLED_TOOLS`**
- `mount(el)` 返回的**清理函数**会被路由自动调用（`render()` 里 `cleanup()`），**这是释放定时器的标准挂载点**
- 首页卡片支持拖拽排序，位置存 `toolbox:home:order`

### 1.2 Rust 侧现状

`src-tauri/src/lib.rs` 已有 3 条命令（`store_read` / `store_write` / `save_file`），
`invoke_handler` 注册模式清晰，**加新命令的成本很低**：

```rust
.invoke_handler(tauri::generate_handler![store_read, store_write, save_file])
//                                                        ↑ 这里追加即可
```

### 1.3 关键约束

| 约束 | 影响 |
|---|---|
| **零构建单文件前端** | 不能用任何前端框架/图表库，UI 必须手写 HTML + 内联 SVG |
| **不引入打包器** | 统计图只能自己画 SVG 或纯 CSS 条 |
| **数据存 `D:\Ai-file\MyTool\data`** | 「数据目录占用」是本地路径，可直接扫 |
| **`capabilities/default.json` 只有 `core:default`** | 自定义命令不受 capability 管辖（现有注释已说明），**新命令无需改权限** |
| **Windows 10 + WebView2** | 用 Win32 API；不要用 `wmic`（Win11 已弃用）|

### 1.4 已确认可用的 Win32 API（来自 `windows-sys 0.61.2`）

> ⚠️ **前置修正**：`windows-sys` 目前只在 `Cargo.lock` 里（传递依赖），
> **`Cargo.toml` 没有直接声明**，必须先加 `[target.'cfg(windows)'.dependencies]` 才能 `use`。
> 详见 **§7.5.1**（含完整 features 清单）。

| 需要的指标 | API | 所在模块 |
|---|---|---|
| 系统总/可用内存、内存负载 | `GlobalMemoryStatusEx` | `Win32::System::SystemInformation` |
| **系统内存全景（更推荐）** | `GetPerformanceInfo` | `Win32::System::ProcessStatus`（`psapi`）→ 见 §7.5.2 |
| 本进程内存（工作集/私有） | `GetProcessMemoryInfo` | `Win32::System::ProcessStatus`（`psapi`） |
| 当前进程句柄 | `GetCurrentProcess` | `Win32::System::Threading` |
| 进程 CPU 时间 | `GetProcessTimes` | `Win32::System::Threading` |
| **系统整体 CPU 占用** | `GetSystemTimes` | ⚠️ **`Win32::System::Threading`**（此处原写 SystemInformation，已修正） |
| 磁盘容量/可用 | `GetDiskFreeSpaceExW` | `Win32::Storage::FileSystem` |
| 盘符类型（本地/移动/网络） | `GetDriveTypeW` | `Win32::Storage::FileSystem`（常量在 `System::WindowsProgramming`）|
| CPU 核数（**推荐，替换下行**） | `GetNativeSystemInfo` | `Win32::System::SystemInformation` |
| 逻辑处理器数（繁琐，可不用） | `GetLogicalProcessorInformationEx` | `Win32::System::SystemInformation` |
| 物理内存条实际容量 | `GetPhysicallyInstalledSystemMemory` | `Win32::System::SystemInformation` |
| 开机时长 | `GetTickCount64` | `Win32::System::SystemInformation` |

结构体 `MEMORYSTATUSEX`、`PROCESS_MEMORY_COUNTERS_EX`、`PERFORMANCE_INFORMATION`、`SYSTEM_INFO` 也都在。

> **CPU 占用怎么算**：`GetSystemTimes` 给的是**累计** tick（idle/kernel/user），
> 需要**两次采样做差**才能得出百分比 → 这就是为什么必然要有"采样间隔"的概念。

## 2. 模块定位与边界

### 2.1 两种定位，建议选后者

| 方案 | 说明 | 评价 |
|---|---|---|
| **A. 并列为第 5 个工具** | 和 internlog/sketch 一样出现在首页卡片 | 会占一个卡片位，且"系统状态"更像应用自身的设置面板，不像"工具" |
| **B. 作为「设置/关于」面板**（推荐） | 首页底部 `data-bar` 旁加一个低调入口，不占卡片位 | 语义准确：这是**应用自身的信息**，不是"用它来干活的工具" |

**推荐 B**：在首页现有这一块旁边加入口：

```html
<div class="data-bar">
  <button class="btn btn-sm" id="dataExport">导出全部数据</button>
  <button class="btn btn-sm" id="dataImport">导入全部数据</button>
  <button class="btn btn-sm" id="openSysinfo">系统状态</button>   <!-- 新增 -->
  <span class="hint">…</span>
</div>
```

点开后**要么**跳到一个独立页面（`#sysinfo`，加进路由），**要么**弹出模态框。
考虑到本项目已有成熟的 `askConfirm` / `askForm` 模态体系，且系统状态**需要持续刷新**（模态框更适合放定时器、关闭即销毁），**推荐用模态框**。

> 但如果你希望它"像个正经工具"、能拖拽排序、能被 `ENABLED_TOOLS` 统一管理，那就选 A。**这是最需要你拍板的一点**，见 §7 决策点 1。

### 2.2 明确不做的事

- ❌ 不做"进程管理器"（列全部进程、结束进程）—— 那是另一个量级的工具，且有风险
- ❌ 不做"性能历史曲线持久化"—— 瞬时值 + 会话内曲线足够，落盘会污染 `store.json`
- ❌ 不做自动优化/一键清理 —— 第一版要**纯只读**，避免误删你的数据

### 3.2 需要的新命令

#[tauri::command]
fn sysinfo() -> Result<String, String>   // 返回 JSON 字符串

/// 数据目录占用（单独一条，因为要扫目录，可能稍慢）

### 3.3 Rust 侧实现骨架（约 150 行）

```rust
use windows_sys::Win32::System::SystemInformation::{GlobalMemoryStatusEx, MEMORYSTATUSEX};
use windows_sys::Win32::System::ProcessStatus::{GetProcessMemoryInfo, PROCESS_MEMORY_COUNTERS_EX};
use windows_sys::Win32::System::Threading::{GetCurrentProcess, GetProcessTimes, GetSystemTimes};
use windows_sys::Win32::Storage::FileSystem::GetDiskFreeSpaceExW;

#[tauri::command]
fn sysinfo(data_dir: String) -> Result<String, String> {
    let mut out = serde_json::Map::new();

    // ---- 系统内存 ----
    unsafe {
        let mut ms: MEMORYSTATUSEX = std::mem::zeroed();
        ms.dwLength = std::mem::size_of::<MEMORYSTATUSEX>() as u32;
        if GlobalMemoryStatusEx(&mut ms) != 0 {
            let total = ms.ullTotalPhys;
            let avail = ms.ullAvailPhys;
            out.insert("mem_total".into(), total.into());
            out.insert("mem_avail".into(), avail.into());
            out.insert("mem_percent".into(), ms.dwMemoryLoad.into());
        }
    }

    // ---- 本进程内存 ----
    unsafe {
        let mut pmc: PROCESS_MEMORY_COUNTERS_EX = std::mem::zeroed();
        let h = GetCurrentProcess();
        if GetProcessMemoryInfo(
            h,
            &mut pmc as *mut _ as *mut _,
            std::mem::size_of::<PROCESS_MEMORY_COUNTERS_EX>() as u32,
        ) != 0 {
            out.insert("proc_working".into(), pmc.WorkingSetSize.into());
            out.insert("proc_private".into(), pmc.PrivateUsage.into());
        }
    }

    // ---- 磁盘（项目所在盘）----
    unsafe {
        let wide: Vec<u16> = "D:\\\0".encode_utf16().collect();
        let (mut free, mut total, mut total_free) = (0u64, 0u64, 0u64);
        if GetDiskFreeSpaceExW(wide.as_ptr(), &mut free, &mut total, &mut total_free) != 0 {
            out.insert("disk_total".into(), total.into());
            out.insert("disk_free".into(), free.into());
        }
    }

    // ---- CPU：需要两次采样，所以这条命令要能"承接上次采样" ----
    // 方案：把上一次的 idle/kernel/user 累计值存在 State 里，两次调用做差
    // （详见 §3.4）

    Ok(serde_json::Value::Object(out).to_string())
}
```

### 3.4 CPU 占用的正确做法

`GetSystemTimes` 返回**累计 tick**，必须做差：

```rust
#[derive(Default)]
struct CpuSample(Mutex<Option<(u64, u64, u64)>>);   // (idle, kernel, user)

fn cpu_percent(state: &State<'_, CpuSample>) -> f64 {
    unsafe {
        let (mut idle, mut kern, mut user) = (0u64, 0u64, 0u64);
        if GetSystemTimes(&mut idle as *mut _ as *mut _, &mut kern as *mut _ as *mut _, &mut user as *mut _ as *mut _) == 0 {
            return -1.0;
        }
        let mut g = state.0.lock().unwrap();
        let prev = g.replace((idle, kern, user));
        match prev {
            None => -1.0,   // 首次采样无基准，返回 -1 表示"测量中"
            Some((pi, pk, pu)) => {
                let d_idle = idle - pi;
                let d_total = (kern - pk) + (user - pu);   // 注意：kernel 已含 idle
                if d_total == 0 { return -1.0; }
                100.0 * (1.0 - d_idle as f64 / d_total as f64)
            }
        }
    }
}
```

> **踩坑提示**：Windows 的 `kernel` 时间**已经包含** `idle` 时间，
> 所以总时间 = `(kernel-pk) + (user-pu)`，**不要再加一次 idle**。这是常见错误。

### 3.5 前端轮询与销毁（**最关键的部分**）

鉴于本项目已经踩过「mermaid 常驻内存」的坑，这个模块的定时器必须严格管理：

```js
mount(el) {
  let timer = null, alive = true;

  async function refresh() { /* 调 sysinfo + dir_usage，更新 DOM */ }

  refresh();                                    // 立即拉一次
  timer = setInterval(refresh, 3000);           // 3 秒刷新

  // 页面隐藏时暂停（省电、省 CPU）
  function onVis() { document.hidden ? stop() : start(); }
  document.addEventListener('visibilitychange', onVis);

  function stop() { if (timer) { clearInterval(timer); timer = null; } }
  function start() { if (!timer && alive) { refresh(); timer = setInterval(refresh, 3000); } }

  return function dispose() {                   // ← 路由会自动调用
    alive = false;
    stop();
    document.removeEventListener('visibilitychange', onVis);
  };
}
```

**三条铁律**（都来自这个项目已有的教训）：
1. 定时器必须在 `dispose` 里 `clear`
2. `visibilitychange` 监听器必须解绑
3. 异步回调里检查 `alive`，避免关闭后还去写已卸载的 DOM

**轮询间隔建议 3 秒**：`GetSystemTimes` 做差需要间隔，间隔太短 CPU% 抖动大（1 秒太敏感），太长则"看起来卡"（10 秒太迟钝）。3 秒是舒适区。

### 6.2 【值得做】阈值告警

不是被动看，而是主动提醒：

- 磁盘可用 **< 10 GB** → 首页顶部一条温和的黄色提示
- 存档体积 **> 5 MB**（说明画板插了大图）→ 提示"考虑启用图片外置"
- `target` **> 5 GB** → 提示"可以清理构建缓存"

**这与前几轮的优化直接呼应** —— 上次是"事后清理 8.6 GB"，这次变成"事前就知道要清理"。

### 6.3 【可选】诊断用的"内存基线对比"

你已知的基准（我记录在案）：

| 场景 | renderer |
|---|---|
| 未加载 mermaid | 20~35 MB（预期） |
| 加载过 mermaid | 69 MB |

模块可以**显示当前处于哪个状态**，验证上次的优化是否真的生效。

### 6.4 【不建议】做成"任务管理器"

列进程、结束进程这类功能：
- 需要额外权限（`OpenProcess` + `PROCESS_TERMINATE`）
- 误操作后果严重
- 系统自带任务管理器做得更好

**守好"只读诊断"这个边界就够了。**

## 7. 决策点（需要你拍板）

### 决策点 1：入口形态
- **B. 设置/关于面板 + 模态框**（我推荐）
- **A. 第 5 个工具卡片**（能拖拽排序，走 `ENABLED_TOOLS`）

### 决策点 2：做到第几档
- **只做第一档**（推荐）：纯只读，约 310 行，一次做完
- **第一 + 第二档**：加上构建缓存/存档明细/运行期可视化
- **全做**：含清理操作（风险显著上升）

### 决策点 3：系统 CPU 占用要不要
- 要 —— 需要多一个 `CpuSample` state + 两次采样逻辑（约 20 行）
- 不要 —— 只显示内存和磁盘，能省掉采样状态管理

### 决策点 4：要不要 6.1 的诊断报告导出
- 要 → 复用 `saveBlob`，约 30 行
- 不要 → 先只看

## 7.5 可扩展 API 全清单（摸过一遍 windows-sys 源码的结论）

> 本节回答「**还有什么其他的 api 可以利用的**」。所有条目均已**逐一核对 `windows-sys 0.61.2` 源码**（`.../registry/src/.../windows-sys-0.61.2/src/Windows/Win32/**`），不是凭印象写的。

### 7.5.1 前提：一个必须先说清楚的坑

**`windows-sys 0.61.2` 目前在 `Cargo.lock` 里，但 `Cargo.toml` 没有直接声明它 —— 它是被传递依赖带进来的。**
直接 `use windows_sys::...` 会编译失败。

```toml
# src-tauri/Cargo.toml  追加（成本极低：包已在本地缓存，不会重新下载）
[target.'cfg(windows)'.dependencies]
windows-sys = { version = "0.61", features = [
  "Win32_Foundation",
  "Win32_Storage_FileSystem",
  "Win32_System_SystemInformation",
  "Win32_System_ProcessStatus",
  "Win32_System_Threading",
] }
```

> **比"零新增依赖"更准确的说法**：*零新增下载、零新增编译单元*（crate 本身要编一次，但体量小、无 proc-macro，几秒的事）。
> 好处是**只编你启用的 feature**，后面按需加 feature 即可。

**已核实的 0.61.2 feature 可用性**（共 223 个 `Win32_*` feature，下列全部存在）：

`Win32_System_SystemInformation` · `Win32_System_ProcessStatus` · `Win32_System_Threading` · `Win32_System_Memory` · `Win32_System_Power` · `Win32_System_JobObjects` · `Win32_System_Performance` · `Win32_System_EventLog` · `Win32_System_Shutdown` · `Win32_System_Environment` · `Win32_System_Services` · `Win32_System_Registry` · `Win32_System_WindowsProgramming` · `Win32_System_SystemServices` · `Win32_System_SecurityCenter` · `Win32_System_RestartManager` · `Win32_System_Wmi` · `Win32_Storage_FileSystem` · `Win32_UI_Shell` · `Win32_System_Diagnostics_Debug` · `Win32_System_Diagnostics_ToolHelp` · `Win32_System_Diagnostics_Etw`

### 7.5.2 ⭐ 值得纳入第一次就做（第一档范围内）

| 指标 | API | 所在位置 | 为什么值得 |
|---|---|---|---|
| **系统级内存全景（一次拿全）** | `GetPerformanceInfo` | `System::ProcessStatus`（`psapi.dll`） | **强烈推荐，替代 `GlobalMemoryStatusEx`**。一个结构体给出：`CommitTotal/Limit/Peak`（提交内存）、`PhysicalTotal/Available`、`SystemCache`（**系统缓存**）、`KernelTotal/KernelPaged/KernelNonpaged`、`PageSize`、`HandleCount`、**`ProcessCount`**、**`ThreadCount`**。比原来计划的"只看总/可用"信息量高一个数量级，**且进程数/线程数正好是你之前截图里关心的东西** |
| **物理内存条真实容量** | `GetPhysicallyInstalledSystemMemory` | `System::SystemInformation` | 返回 KB。与 `ullTotalPhys` 一比，就能算出**硬件保留了多少**（集显吃掉的），排障时有用 |
| **CPU 核数与架构** | `GetNativeSystemInfo` | `System::SystemInformation` | `SYSTEM_INFO` 里有 `dwNumberOfProcessors` / `dwProcessorArchitecture` / `dwPageSize`。比 `GetLogicalProcessorInformationEx` **简单太多**，核数展示够用了（原来的方案过于复杂，建议换掉） |
| **CPU 累计 tick** | `GetSystemTimes` | ⚠️ **`System::Threading`，不是 SystemInformation** | 原方案 §1.4 表格里位置写错了，实施时按 **Threading** 导入。签名收的是 `FILETIME*`（`Win32::Foundation`） |
| **盘符类型** | `GetDriveTypeW` | `Storage::FileSystem` | 常量在 **`System::WindowsProgramming`** 里（`DRIVE_FIXED=3` / `DRIVE_REMOVABLE=2` / `DRIVE_REMOTE=4` / `DRIVE_CDROM=5` / `DRIVE_RAMDISK=6` / `DRIVE_NO_ROOT_DIR=1` / `DRIVE_UNKNOWN=0`）。用来给磁盘列表打标签（本地盘/移动盘/网络盘） |
| **开机时长** | `GetTickCount64` | `System::SystemInformation` | 已经有，保留 |
| **数据目录/项目目录真实占用** | 纯 `std::fs` 递归 | — | 不需要 API，`std::fs::read_dir` 递归累加即可。注意 `src-tauri/target` **几万个文件、要几百毫秒到几秒**，必须放**独立线程 + 单独命令**，不能塞进 `sysinfo()` 里拖慢主面板 |

> **回收站占用** `SHQueryRecycleBinW`（`UI::Shell`，`shell32.dll`）返回 `SHQUERYRBINFO{i64Size, i64NumItems}`。
> 属于"值得但可缓一步" —— 因为它要引入 `Win32_UI_Shell` feature（`shell32` 体量不小）。**放第二档更合适。**

### 7.5.3 可选（看你兴趣，放第二/三档）

| 指标 | API | 代价 / 注意事项 |
|---|---|---|
| **电池 / 供电状态** | `GetSystemPowerStatus`（`System::Power`） | `SYSTEM_POWER_STATUS{ACLineStatus, BatteryFlag, BatteryLifePercent,...}`。**你是台式机，这栏永远是"接交流电"**，价值不大；但如果哪天用笔记本跑，加 5 行就能显示 |
| **系统级 PDH 计数器**（CPU/磁盘队列/网络） | `PdhOpenQuery` / `PdhAddEnglishCounterW` / `PdhCollectQueryData` / `PdhGetFormattedCounterValue` | **`System::Performance`**，共 60+ 个 `Pdh*` 函数。能拿到任务管理器同款指标（`\Processor(_Total)\% Processor Time` 等）。**代价**：需要两次采样 + 计数器路径字符串，约 80 行；**且和我们自己算的 CPU% 重复**。除非你要"磁盘活动时间 / 网络吞吐"，否则不必 |
| **进程快照/线程列举** | `CreateToolhelp32Snapshot` + `Process32FirstW/NextW`（`Diagnostics::ToolHelp`） | 能自己算出"webview2 有几个进程、各占多少内存"。**但 §6.4 已明确不做任务管理器**，列进程属于越界，不做 |
| **系统事件日志** | `EvtQuery`/`EvtNext`/`EvtRender`（`System::EventLog`，`wevtapi.dll`） | 可读取应用崩溃/系统告警事件。**引入 `wevtapi` 依赖 + 需要解析 XML**，重；一个"诊断报告"里附最近 5 条错误事件倒是有趣，但**收益/成本比不好**，不建议 |
| **注册表读取** | `RegOpenKeyExW` / `RegQueryValueExW`（`System::Registry`） | 能读系统信息（如 CPU 型号名 `HKLM\HARDWARE\DESCRIPTION\System\CentralProcessor\0\ProcessorNameString`）。⚠️ **这条是真的能让你显示"Intel i5-xxxx"** —— 如果想在面板里显示 CPU 型号，这是唯一轻量途径。注意 32/64 位视图（`KEY_WOW64_64KEY`） |
| **卷标 / 卷文件系统** | `GetVolumeInformationW`（`Storage::FileSystem`） | 显示"NTFS / 卷标"。锦上添花 |
| **显示器分辨率 / DPI** | `GetSystemMetrics`（`UI::WindowsAndMessaging`）、`GetDeviceCaps`（`Graphics::Gdi`） | 调试 UI 尺寸问题时有用，与"系统状态"主题相关性弱 |
| **WMI 查询** | ⚠️ **不可用（重要）** | `System::Wmi` 模块里**只有 1 个函数** `MI_Application_InitializeV1` + 常量，**没有 `IWbemServices` / COM 接口**。`windows-sys` 走的是 MI（Management Infrastructure）裸 C API，**要真正用 WMI 只能额外引入 `windows` crate（COM 支持）或 `wmi` crate** —— 这就是我**不推荐**的原因。**好消息是：你原本想用 WMI 拿的东西（内存/CPU/进程数/磁盘）上面 7.5.2 里全都有，不需要 WMI** |

### 7.5.4 ⚠️ 明确不建议（有副作用）

| API | 为什么不建议 |
|---|---|
| **`EmptyWorkingSet` / `K32EmptyWorkingSet`**（`System::ProcessStatus`） | 可以**主动把自己（或其他进程）的工作集裁掉**，任务管理器里内存数字会立刻变小。但这个项目已经分析清楚了：**236 MB 是 WebView2 的固定门票**，裁掉的页面马上会被换回来（`page fault`），**只是把内存挪到页文件上，实际变慢，数字好看而已**。这正是"自欺欺人式优化"。❌ |
| **`SetSystemFileCacheSize` / `SetProcessWorkingSetSizeEx`** | 同上，且需要更高权限 |
| **`InitiateShutdownW` / `ExitWindowsEx`**（`System::Shutdown`） | 关机/重启/注销 —— **一个个人工具箱不该有这个能力** |
| **`TerminateProcess`**（`Diagnostics::Debug` / `Threading`） | 结束进程，误操作后果严重 |
| **`EmptyRecycleBin`（`SHEmptyRecycleBinW`）** | 清空回收站，不可逆 |
| **`SHEmptyRecycleBin` / `SHFileOperationW` 做删除** | 第三档若真的要做"清理"，**优先用已有的 `explorer` 打开目录让用户自己动手**，不要替用户删 |
| **`PowerSetActiveScheme` / `SetSuspendState`** | 改电源计划、休眠，需要管理员，且与工具箱无关 |

### 7.5.5 Tauri 侧可用的能力（与 Win32 互补）

**`app.path()` —— 零成本拿到 21 个标准目录**（`tauri 2.11.5`，已核对 `tauri::path::PathResolver`）：

`app_cache_dir` · `app_config_dir` · `app_data_dir` · `app_local_data_dir` · `app_log_dir` · `audio_dir` · `cache_dir` · `config_dir` · `data_dir` · `desktop_dir` · `document_dir` · `download_dir` · `executable_dir` · `font_dir` · `home_dir` · `local_data_dir` · `picture_dir` · `public_dir` · `resource_dir` · `runtime_dir` · `temp_dir` · `template_dir` · `video_dir`

**这个的实用价值被低估了**：现在代码里 `DATA_DIR` 是**硬编码字符串** `"D:\\Ai-file\\MyTool\\data"`。
用 `app_local_data_dir()` 可以**优雅地拿到 WebView2 缓存目录的父目录**，做 4.2 那节（EBWebView 38 MB）时不用再拼 `%LOCALAPPDATA%` 字符串：

```rust
// EBWebView 就在 identifier 命名的目录下，不必手拼路径
let wv2 = app.path().app_local_data_dir()?.join("EBWebView");
```

**已装插件（只有 2 个）**：`tauri-plugin-dialog`、`tauri-plugin-single-instance`。

**与"系统状态"相关的、值得考虑安装的官方插件**：

| 插件 | 用途 | 是否推荐 |
|---|---|---|
| `tauri-plugin-os` | 跨平台拿 OS 版本/架构/hostname/CPU 核数（不用自己调 Win32） | **可选**。好处是跨平台；坏处是**多一个插件依赖**、且信息量不如直接调 Win32 细。本项目只在 Windows 跑，**自己调更划算** |
| `tauri-plugin-process` | `restart()` / `exit()` —— "重启应用"按钮 | **可选**。第三档"清理 WebView2 缓存"必须重启才生效时会用到 |
| `tauri-plugin-opener` | 打开 URL/文件/目录（比 `tauri-plugin-shell` 轻） | **第二档"打开数据目录"用它**，比手动拼 `explorer` 命令干净 |
| `tauri-plugin-log` | 结构化日志 → 文件 | **可选**。如果做"诊断报告导出"，日志是很好的素材 |

> **原则**：能一条 `GetXxx` 解决的，不要装插件。插件的价值在**跨平台**，而本项目明确了只在 Windows 10 上跑。

### 7.5.6 一句话结论

**原始需求（内存占用 + 磁盘占用）用 §3 的五六个 API 就够了。**
最有性价比的**增量**是这三个，都几十行以内：

1. **`GetPerformanceInfo`** —— 一次拿到提交内存/系统缓存/内核内存/进程数/线程数，比原方案丰富得多
2. **`GetNativeSystemInfo`** —— 替换掉原方案里最繁琐的 `GetLogicalProcessorInformationEx`
3. **注册表读 CPU 型号名** —— 唯一能让面板显示"Intel Core i5-XXXX"的轻量办法

**其余的（PDH、ToolHelp、EventLog、WMI）都不建议**：要么与已有能力重复，要么成本远大于收益，要么会把"只读诊断工具"带偏成"任务管理器"。

## 8. 验证方式

新增 `tools/verify-sysinfo.js`（沿用现有 Node vm 单测风格）：

```
[1] sysinfo 命令返回 JSON 可解析
[2] 字段齐全：mem_total/mem_avail/mem_percent/disk_total/disk_free/proc_working/...
[3] 数值合理性：mem_avail <= mem_total；disk_free <= disk_total；mem_percent ∈ [0,100]
[4] CPU 首次调用返回 -1（无基准），第二次为 [0,100]
[5] dir_usage 对不存在路径返回 0 而非报错
[6] 前端：mount 后定时器已启动；dispose 后定时器已清除（用 fake timer 断言）
[7] 前端：visibilitychange 触发时暂停/恢复
```

**第 6、7 条最重要** —— 定时器泄漏正是这个项目已经踩过的坑。

真机验证：
```bash
npx -y @tauri-apps/cli@2 dev
```
1. 打开面板，数值与任务管理器**逐项对照**（内存、CPU、磁盘）
2. 关掉面板 → 任务管理器确认 CPU 回落（说明轮询确实停了）
3. 反复开关 10 次 → 内存不应持续上涨（没有监听器泄漏）

## 10. 一句话总结

**这个模块技术上很轻**：所需 Win32 API 全在已有依赖里，约 300 行、零新增依赖、不碰核心存储。

**它真正的价值不是"能看内存"**，而是把前几轮那些**只能靠命令行 `du` 和任务管理器猜**的东西，
变成**打开就能看见的数字** —— 8.6 GB 的构建缓存在哪、C 盘那 38 MB 是什么、存档里哪一项在膨胀、上次的 mermaid 优化到底省了多少。

**建议**：先做**第一档 + 6.1 诊断导出**（约 340 行），纯只读、零风险。
第三档的"清理操作"如果要做，**务必单独一轮**，并把"移动而非删除"作为默认行为。

**补充（§7.5 的结论）**：如果想让面板信息更值钱，就在第一档里**顺手加这三个**——
`GetPerformanceInfo`（进程数/线程数/系统缓存/内核内存）、`GetNativeSystemInfo`（核数，替换掉繁琐的 `GetLogicalProcessorInformationEx`）、
注册表读 CPU 型号名。三个加起来不到 60 行，但展示效果提升明显。
**其余的 PDH / ToolHelp / EventLog / WMI 全部不做** —— 要么重复、要么昂贵、要么越界。
